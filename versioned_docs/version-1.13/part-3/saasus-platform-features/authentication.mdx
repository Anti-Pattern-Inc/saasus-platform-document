Authenticate users at sign-in and obtain tokens for use in your SaaS application.  
Use the login pages or integrate SaaSus API into custom sign-in pages.

Related API links use operation names from Auth API.

## Sign-in and sign-up

Let SaaS users register new accounts and sign in to existing accounts.  
Use the login pages or integrate SaaSus API into custom sign-in pages. The login pages also support resending temporary passwords and recovering forgotten passwords.

For custom sign-in pages, use the APIs to initiate authentication with SRP_A and respond with an SRP signature.  
Also implement responses when MFA verification or initial password setup is required.

### Repeated sign-in failures

Repeated incorrect passwords can temporarily lock the account and prevent sign-in.  
The lock normally clears automatically after a period of time. The exact number of attempts is not disclosed.

## External identity providers

Sign in using Google or an external identity provider that supports SAML.  
Google sign-in starts on the regular login page, while SAML sign-in starts at a tenant-specific login URL.  
In both cases, authentication takes place with the connected identity provider.

Domain and email sending domain verification must be completed before using an external identity provider.

## Multi-factor authentication (MFA)

Verify users with codes from an authenticator app or email in addition to their passwords.  
Implement authenticator registration and MFA settings pages in your SaaS application; users can enter verification codes on the login pages when signing in.

Custom sign-in pages also require API integration for verification code validation.

### Using email MFA

Verification codes sent by email are valid for three minutes. This duration cannot be changed.  
Users must enter the code and complete sign-in within that time.

Users with email MFA enabled cannot reset their passwords through the login pages.  
If they forget their password, an administrator resets it through User Management in the SaaS Operations Console.  
See [User Management (Legacy UI): Search, Create, Edit, Add to Tenant](/docs/part-5/user-management/user-crud) for the steps.

## Device authentication

Remember trusted devices so users can skip MFA code entry on subsequent sign-ins.  
In the SaaS Development Console, choose “Always remember,” “User opt-in” (remember only when the user chooses to), or “Do not remember.”

| Feature | Details | Related APIs |
| --- | --- | --- |
| Configure how trusted devices are remembered | Choose “Always remember,” “User opt-in,” or “Do not remember.” With user opt-in, devices are remembered only when users choose to remember them.<br />References: [Authentication Method Settings](/docs/part-4/user-authz-settings/authentication-method-settings) | [GetSignInSettings](/docs/reference/auth-api#tag/authInfo/operation/GetSignInSettings) [UpdateSignInSettings](/docs/reference/auth-api#tag/authInfo/operation/UpdateSignInSettings) |
| Confirm device registration | Confirm a device for registration as a trusted device during sign-in. The login pages use this API internally. | [ConfirmDevice](/docs/reference/auth-api#tag/saasUser/operation/ConfirmDevice) |
| Update device remembered status | Update a device’s remembered status. On the login page, selecting “Remember device” marks the device as remembered. Clearing the checkbox does not remove a previously remembered status. | [UpdateDeviceStatus](/docs/reference/auth-api#tag/saasUser/operation/UpdateDeviceStatus) |

</FeatureTable>

## Tokens and credentials

Obtain credentials for signed-in users and manage their sign-in state.  
Exchange temporary codes received from the login pages for tokens. You can also refresh tokens or revoke refresh tokens.

| Exchange temporary codes with PKCE | Specify PKCE parameters in the URL used to open the login pages. After authentication completes, your application exchanges the temporary code for tokens using the code verifier it retained. | [ExchangeAuthCredentials](/docs/reference/auth-api#tag/credential/operation/ExchangeAuthCredentials) |
| Refresh authentication tokens | ID tokens expire after one hour. Use a refresh token to obtain a new ID token and access token and maintain the user’s sign-in state in your SaaS application.<br />References: [Authentication Methods](/docs/part-6/usecase/authentication-methods) | [GetAuthCredentials](/docs/reference/auth-api#tag/credential/operation/GetAuthCredentials) |
| Revoke refresh tokens | Use to stop further token refreshes. Also implement removal of application cookies or other local session data. | [RevokeToken](/docs/reference/auth-api#tag/credential/operation/RevokeToken) |
| Configure refresh token validity | Set the refresh token lifetime.
